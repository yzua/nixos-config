# Repository guidance

## Where to work and how to verify

- `flake.nix` wires the `PC` host and standalone `yz@PC` Home Manager profile. For Firefox profiles, GNOME input sources, MIME defaults, or user secrets, read the relevant `README.md` section before changing them; `just home-preview` does not show dconf changes.
- `just verify` runs `nix flake check --no-build --no-write-lock-file .`; `just check` also checks Nix file headers (`just headers`), repo-declared package duplicates (`just pkgs`), and warns about untracked `.nix` files. `just status` evaluates active, saved, and desired generations without building or switching.
- For workflow changes, start in `justfile`: `scripts/config.sh` centralizes output selection for its recipes and checkers; `scripts/check-nix-headers.sh`, `scripts/check-packages.sh`, and `scripts/status.sh` implement `just headers`, `just pkgs`, and `just status`. Keep selection logic in `config.sh` rather than duplicating it.
- `just preview` builds/diffs the NixOS closure; `just home-preview` builds/diffs the separate Home Manager activation. They save links under `${XDG_STATE_HOME:-$HOME/.local/state}/nixos/`. Only `just switch` / `just home-switch` activate, after reviewing the respective preview; run the home switch without sudo. Unqualified `nixos-rebuild` uses `/etc/nixos`, not this flake.
- When moving packages or settings from NixOS to Home Manager, preview and switch Home Manager **before** previewing and switching NixOS, so user apps do not disappear in between.

## Configuration structure and style

- Keep `flake.nix` focused on inputs, outputs, and project tooling. Put hardware, storage, boot policy, hostname, account, and `system.stateVersion` in `hosts/<host>/`; keep generated hardware files intact. Import reusable NixOS modules explicitly from `modules/nixos/`, with a small `base.nix` and opt-in features such as `development.nix`, `gnome.nix`, and `numtide-cache.nix`.
- Keep Home Manager standalone: the dedicated `home-manager/home.nix` sets the account and imports focused modules from `home-manager/modules/`. NixOS owns system services and intentionally system-wide packages; Home Manager owns user apps and preferences. Give each setting one clear owner rather than declaring it in both layers.
- Prefer direct Nix option definitions, explicit imports, and filenames that name the actual feature. Add an enable option, role hierarchy, or host inventory only when real shared behavior needs it; this single-host config does not need to mirror the old repo's structure. Use the read-only `just fmt-check` and `just lint` recipes from the dev shell for formatting and static analysis (see `README.md`).

## Rules to preserve

- Start each `.nix` file with a short `#` purpose header before its expression; add a noteworthy constraint there only when it helps future editors/agents. Keep generated files' existing warning headers intact. `just headers` checks tracked and untracked Nix files for missing headers.
- Apply portability to **all reusable repository content**, not just Nix or shell scripts: modules, workflows, app settings, templates, tests, and documentation examples. Do not bake a particular username, home directory, hostname, device path, or flake output name into shared behavior. Derive values from the selected configuration or caller, or accept explicit inputs; when selection is ambiguous, ask for an override instead of guessing (`NIXOS_CONFIG` and `HOME_CONFIG` for the just workflow).
- Keep concrete machine/user identities only where they intentionally define that machine or account (for example, a host module, a dedicated home profile, and the flake outputs that connect them). Documentation may describe this machine's actual migration, but reusable instructions and examples should not assume its identity. A friend should be able to supply their own host/user configuration without editing shared logic.
- Before adding or installing a package, check whether its output can be downloaded from the configured, trusted Nix binary caches rather than compiled locally. For packages that would require a substantial local build, look for a maintained prebuilt/binary variant in Nixpkgs (or an official binary packaged through Nix) and prefer it when the features and platform fit. Do not silently add untrusted caches, fetch unverified binaries, or start a lengthy source build without first explaining the tradeoff and getting approval.
- Preserve `system.stateVersion` and `home.stateVersion` from their initial installations. Do not bump them for a routine Nixpkgs or Home Manager update; change them only as part of a deliberate, reviewed state migration.
- Keep secrets out of Git and the Nix store. Never commit credentials, tokens, passwords, or private keys, or place plaintext secrets in Nix values that become store paths. Discuss a suitable secret-management approach before introducing one.
- Keep dependency changes focused: do not update `flake.lock` or add unrelated inputs as part of another task. Review any intended lockfile changes and their build previews separately. If a fixed-output hash mismatches, verify the intended upstream artifact before accepting a new hash.
- After changing NixOS or Home Manager configuration, run `just check` and the relevant `just preview` or `just home-preview` when feasible; first get approval if the preview would require a substantial local build. Report validation failures instead of activating a configuration to test it.
- Preserve activation guards: the selected NixOS hostname must match the running host unless a hostname change is explicitly approved; the selected Home Manager user and home directory must match the caller. Do not bypass the reviewed-build/stale-build checks or activate a configuration during `check` or `status`.
- Git flakes do not see new untracked Nix files. Stage new `.nix` modules before evaluating or previewing them.
